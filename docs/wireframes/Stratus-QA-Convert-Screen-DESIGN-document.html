Convert Test Cases — the main screen, in detail

This is the heart of the tool: where a tester turns manual test cases into an automatic test. Designed so a non-technical person can use it without training — no jargon, one clear action per step, safe by default. Three states are shown: before, during, and after conversion. Every numbered dot is explained in the tables below.

State A — what every element is, and why

ElementWhat it is & why it's easy
1Title + one-line promiseSays what the page does in plain words — "turn manual steps into an automatic test, no coding". Sets the expectation immediately; no product jargon like "YAML" or "conversion pipeline".
23-step progress railShows the whole journey up front: Add steps → Check settings → Convert & review. Behavior: ticks are automatic (step 1 ✓ when a file is added; step 2 ✓ right after, since every setting is pre-filled; step 3 ✓ when conversion finishes). Completed steps are clickable to go back — with everything preserved — but forward steps are never clickable (no empty dead-ends). If the user goes back and changes the file or a setting after converting, step 3 un-ticks and the button becomes "Convert again →", so a stale result can never be run.
3"How do you want to add your test steps?"A question, not a menu. Three big cards instead of hidden tabs — the user picks the way that matches how they already work.
4Input method cards (Upload / Paste / Describe)Upload a file — the Excel (.xlsx) test-case files testers already write (Google Sheets users download as Excel first). Paste your steps — for steps living in emails or Word; pasted text goes through the same plain-English understanding as "describe it". Just describe it — type what to test in your own words. The selected card gets a dark border so the choice is visible.
5Drop zoneBig target, two ways to use it (drag, or click "choose from computer"), and it states the file type in plain terms. One file at a time — but a single file can carry a whole ticket's test cases across many screens, and the tool splits them correctly.
6"Download an example file"The single best helper for a first-time user: a ready-made sample showing what a test case file looks like. Removes the "am I doing this right?" fear.
7Added-file rowInstant feedback after upload: file name, how many test cases we found inside, and the ticket number we auto-detected. A quiet "Remove" undo — mistakes are cheap.
8"Check the settings — we filled these in for you"The framing matters: the user checks settings, they don't fill in settings. Everything below is pre-filled with a sensible answer; the user can simply scroll past.
9Test nameAuto-filled from the file name. Only exists so the test is findable later in the library. Editable, never required.
10Ticket number (optional)Auto-detected from the file name (e.g. STRAT-27678). Connects the test to the ticket so release reports can prove what was tested. Clearly marked optional.
11"Where should the test run?"A dropdown of servers with friendly names and a green health dot — "Test server (safe — not the real store data)". The helper line kills the #1 fear of non-technical users: am I going to break the real system? Answer: never.
12Practice run / Full run toggleInstead of technical "read-only vs write mode": "Practice run — look, but change nothing" (default) vs "Full run — create and edit test data". Safe choice pre-selected; the words describe consequences, not modes.
13The one big button"Convert my test cases →" — the only dark, full-width button on the page. There is never a question about what to press next.
14Reassurance line"Takes about a minute. Nothing will run until you press Run yourself." Tells them the cost (a minute) and removes the fear that pressing the button triggers something big.
15"What happens when you press Convert?"A side panel that explains the magic in four plain sentences — read your steps, find the screens, build the test, ask when unsure. Builds trust before the first click; experienced users just ignore it.

State C — explanation

ElementWhat it is & why it's easy
19Result in one sentence"We understood 19 of your 22 steps." Not a percentage, not a "confidence score" — a sentence anyone understands, with two chips: green = ready, amber = needs you. It celebrates what worked before pointing at what didn't.
20"Help us with these 3 steps"The unclear steps are framed as the tool asking for help — not the user having made errors. This flips the emotional experience from "I failed" to "it needs me".
21Question card + plain answer boxEach card shows: the user's original sentence (so they recognise it), one specific question ("Which screen is the Brand box on?"), and a free-text box where they answer in their own words — the AI translates the answer into the technical fix. Example text in the box shows what a good answer looks like.
22"Skip for now"Every question can be skipped — the test runs without that step and the report clearly lists it as skipped. Nobody is ever blocked by one confusing step.
23"See the 19 steps we understood" (folded)Success is folded away by default — the user only reviews it if they want to. One click opens the full list.
24Steps written back in plain EnglishEach understood step is shown as a sentence — "Click the New button", "Type 'AUTOTEST-001' into the Style box" — so the tester can proofread the automation without reading any code. This is the trust-builder.
25"Show the technical file (for developers)"The YAML exists — but hidden behind one small link. Technical users get everything; non-technical users never see a line of code.
26Three finish actionsRun the test now (the dark primary — the natural next step), Save to my library (keep it for a release later), Start over (quiet, grey, no harm). One obvious choice, two safe alternatives.
27Autosave note"Saved automatically — close this page and come back anytime." Removes the last anxiety: nothing can be lost by walking away.

The 6 rules that keep this screen non-technical

Worth keeping next to the build — every future change to this screen should pass these.

1 · Plain words, everywhere
No "YAML", "parse", "selector", "confidence score" on the main path. It's "your test steps", "the automatic test", "steps that need you". Technical vocabulary lives only behind the developers' link (№25).
2 · One big button per stage
At any moment there is exactly one dark button — Convert (A), then Run (C). Users never choose between equal-looking options.
3 · Nothing required except the file
Every field is pre-filled or optional. The shortest possible journey is: drop file → Convert → answer 0–3 questions → Run. Two clicks plus a drag.
4 · Safe by default
Practice run pre-selected, tests only run on the test server, and nothing executes until the user presses Run. The screen says these things out loud, because feeling safe is a feature.
5 · Problems are questions, not errors
The tool never says "parse failure at line 14". It quotes the user's own sentence and asks one specific question with a free-text answer box. Skipping is always allowed.
6 · Nothing can be lost
Autosave everywhere, Remove/Cancel/Start-over are always visible but quiet, and coming back later is explicitly promised on-screen.
